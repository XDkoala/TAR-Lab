# TAR-Lab 初版需求说明

状态：草案，待确认。本文只描述“要做什么”，架构与技术选型另行讨论，并以本文为依据。

## 1. 定位

TAR-Lab（Trusted Autonomous Research Lab）是一个开源的自动科研平台：从用户的一句话或详细要求出发，完成调研、选题、实验设计与执行、分析、论文撰写和模拟审稿，并具备自修复与自迭代能力。

- AI-Scientist-v3 只是平台中的一个可替换实验引擎，不是系统主体。
- 先开源，用户自行部署、自带模型账号；以后再考虑在线服务。
- 核心价值是科研能力，不是界面。第一版只做终端交互。

## 2. 研究范围

- 首版：可全程在电脑上完成的研究（计算机、人工智能、数学），优先服务具身智能与世界模型方向。
- 以后：机器人、生物、材料等需要人机协作或实体实验的领域。
- “执行实验”抽象为“交给某个执行者并等待结果”。首版只实现本机代码执行者，预留服务器、仿真平台、真机和人工实验员等执行者接口。
- 仿真器、数据集、基准、算力由用户和课题决定，系统不得写死；首版算力为本机 GPU，预留服务器。

## 3. 用户与交互

- 用户始终只与一个主 Agent（总负责人）对话，专家 Agent 对用户不可见。
- 入口：首版为 CLI；网页、App 后续再做。
- 通知：重要节点、错误、待审批事项通过邮件通知；终端可查看进度、离开期间的事件并完成审批。手机推送后续再做。
- 语言：对话、报告、论文语言分别可配置；首版支持中文和英文。

## 4. 立项

- 输入可以是一句话（如“帮我完成一篇世界模型的论文，达到 CCF B”），也可以是详细计划。
- 主 Agent 负责追问：
  - 先问最核心的问题，次要问题自行决定，每个问题都有默认值；
  - 迁就不愿多答的用户（“你定”即采用默认）；
  - 追问多少由用户设定。
- 选题：用户选、系统推荐、系统自主选择三种方式都支持。
- 用户在立项时设定：预算、时间、审批节点、通知频率、并行策略、改动权限、目标会议或期刊（也可由系统推荐）。
- 系统为预算和时间提供档位，并提示各档位的风险和成功可能性。参考：CCF B 约 200 美元、CCF A 约 1000 美元以上；时长可达一个月或更久。
- 对过分或不可行的要求，系统要提示风险，必要时拒绝。

## 5. 研究流程与产出

- 产出：调研与选题报告、研究报告、代码、实验数据、可投稿论文。
- 调研使用 Undermind MCP，以及论文、开源代码、OpenReview 审稿意见、综述、博客、排行榜等多种来源。
- **实验设计要向人类的已有工作学习，不靠 Agent 凭空构思**；每个关键设计决策都要注明参考来源。
- 可以直接使用或修改开源代码作为基线；必须遵守许可证，并在论文中注明出处。
- 允许并推荐并行：同一项目内同时尝试多个候选题目或方案，快速筛选；条件允许时，多个实验、多个项目可以同时运行。筛选规则（候选数量、预算分配、由谁决定）在立项时设定。

## 6. 审稿与价值判断

- 每次运行都有模拟审稿人，按目标会议或期刊的标准打分。
- 审稿 Agent 与调研 Agent 合作判断课题价值：选题阶段做一次早期评审，论文完成后做一次终审。

## 7. 预算控制与止损

- 系统不能因为预算充足就乱花钱。
- 严禁在细节上反复打磨而迟迟不推进。每个子任务派发时都要限定时间、预算和应交付的产出；主 Agent 持续检查投入与进展，发现停滞或钻牛角尖要及时干预（叫停、换方法或降低要求）。
- 止损条件包括：连续多轮没有进展、发现撞题、预算消耗到一定比例仍无像样结果等。具体阈值由用户设定，系统提供默认值。

## 8. 鲁棒性（最高优先级的非功能需求）

- 额度耗尽、模型不可用、用户暂停、进程或网络意外断开后，都必须能从中断处恢复，不丢失进度。
- 出错要及时、清楚地告知用户。
- 可以跨周、跨月运行；全过程可审计、可回放。

### 等待审批的默认规则

- 不依赖该审批的工作照常进行；依赖它的工作暂停，暂停期间不花钱。
- 发出审批请求时立即发邮件，之后按递增间隔（1 小时、4 小时、12 小时、24 小时）提醒。
- 超过用户设定的期限（默认 3 天）仍无回应时，按立项时的选择处理：采用安全的默认选项继续，或者整个项目挂起，花费降到零。
- 每次提醒和最终处理都写入日志。

## 9. 权限与改动

| 级别 | 例子 | 处理 |
|---|---|---|
| 小改动 | 在项目目录内安装 Python 包、修改代码和配置、下载数据集 | 直接执行，写入日志 |
| 大改动 | 使用 sudo、安装系统软件、修改项目目录外的文件、删除文件、单笔花费超过阈值 | 先告知用户 |
| 需审批 | 用户在立项时指定 | 等待用户批准 |

- 允许在本机直接运行，不强制使用 Docker；允许联网；允许读写项目目录以外的文件。
- sudo 只授予主 Agent。
- 对项目和用户系统的任何改动都必须可以回退，并记录在变更日志中。
- Undermind 的写入、删除、移动类工具默认拒绝；深度检索（`launch_deep_search`）需要单独计入预算并审批。

## 10. 自修复与自迭代

| 类型 | 例子 | 负责方 | 处理 |
|---|---|---|---|
| 用户问题 | 实验代码 bug、环境安装失败、显存不足 | 执行 Agent | 必须设法解决，解决不了就和用户商量 |
| 个性问题 | 用户课题与系统现有能力冲突 | 主 Agent | 只针对当前项目做适配，小改动直接做，大改动先告知用户 |
| 共性问题 | 系统自身的缺陷 | 仅主 Agent | 主动发现，尝试修复并测试，然后上报开发者审核，通过后才合入 |

- 自迭代包括积累经验、改进提示词和策略、修改平台代码。其中修改平台代码与共性问题适用同一规则。
- 上报渠道：开发阶段由主 Agent 直接在 TAR-Lab 仓库开 issue、提 PR。开源用户的上报默认关闭，只有用户同意后才开启；上报前先给用户过目，并去除研究内容。
- 修复不得以关闭完整性检查、修改评分标准、伪造成功或删除失败记录的方式实现。

## 11. 可信

- 系统自身绝不造假：结果可复现，引用真实，不篡改数据、不选择性报告，每个结论都能追溯到具体的实验、数据和代码，能发现并承认自己的错误。
- 用户主动“美化”数据时，系统给出警告但不阻拦，同时记录在案，并在报告中披露。

## 12. 模型

- 首版支持市面上常见的模型厂商，计费方式 API 与订阅 CLI 混用。
- 当前可用：Codex 订阅、Devin 订阅（Claude 只能通过 Devin 使用）；以后可能接入 DeepSeek API。
- 设计方向：Devin（Claude）作为核心执行者，承担选题、实验设计等高难任务；其他模型承担编写代码、运行实验等中低难度任务。档位与模型的对应关系可配置。
- 主 Agent 的模型安排尚未确定，需要在智能和花费之间取得平衡，待原型实测后再定。
- 额度用完或模型不可用时必须有应对（切换备用模型，或暂停并通知用户），具体策略属于第 8 节的鲁棒性设计。
- Devin CLI 支持非交互调用（`-p`）、续接会话（`--resume`）和导出对话记录（`--export`）。订阅条款是否允许大规模自动调用、额度是否够用，尚未核实。在核实之前，Devin 只承担少数最难的任务（如选题和实验设计），其余任务交给其他模型。

## 13. 评测

- 以 AI-Scientist-v3 原版作为基线。仓库保留两份引擎：
  - `engines/ai-scientist-v3-original`：固定在上游提交 `df83138`，永不修改，只用于对比；
  - `engines/ai-scientist-v3`：可以大幅改造的版本。
  - 本地 `upstream-main` 分支继续用于同步上游。
- 测试环节：给系统一些已发表论文的题目让它复现，比较结果是否接近。
- 评测时所有 Agent 统一使用同一个模型，便于量化对比。

## 14. 版本目标与验收

### 第零版

- 功能：基础功能全部打通，包括调研、选题报告、本机 GPU 实验、论文、模拟审稿，以及断点续跑、邮件通知和 CLI。
- 模型：所有 Agent 统一使用 Codex `gpt-6.1-sol`，推理强度 `medium`。
- 两个验收项目：

| | A：基线对比（circpack） | B：完整流程（小型世界模型） |
|---|---|---|
| 目的 | 和原版引擎做量化对比 | 验证第零版的完整流程 |
| 输入 | 两边完全相同：同一份 circpack 任务目录（`task.md`、评估脚本、初始程序） | 一句话，例如“做一篇关于小型世界模型的论文，能在 8 GB 显存上运行” |
| 流程 | 原版引擎与 TAR-Lab 各跑一次实验 | 调研 → 选题报告 → 选题审稿 → 实验（含基线对比和消融）→ 论文 → 终审 |
| 对比或产出 | 只比最终结果：最终得分、花费、耗时；不写论文 | 选题报告、代码、实验数据、论文、审稿意见；论文结构完整、实验真实即合格，审稿只打分、不设门槛 |
| 时长 | 半天以内 | **1 天以内** |
| 规模 | 与原版配置一致 | 环境如 Gymnasium 或 MiniGrid（待定）；单次训练不超过 15 分钟，峰值显存不超过 6 GB；候选方向 2 个 |
| 预算参考 | 约 10 美元 | 约 30 美元 |

预算和规模都是估计值，以实测为准，并用实测数据校准立项时的预算档位。B 同时用来测试断点续跑和等待审批。

### 第一版

- 要求足够智能和灵活。
- 本机 GPU：RTX 5060 Laptop，显存 8 GB。
- 前提：高难度任务（选题、实验设计、审稿等 `high` 档角色）由 Devin 承担，其余档位可用其他模型。开始验收前须确认 Devin 订阅允许这种自动调用、额度够用。
- 验收分两步：先重跑项目 B 并与第零版对比，再用用户手上的真实项目验收。

#### 硬性门槛（全部满足才通过）

1. 完整流程：从一句话需求开始，自行走完调研 → 选题报告 → 选题审稿 → 用户批准 → 实验（基线、方法、消融，每组至少 2 个随机种子）→ 封存的最终评估 → 分析 → 论文 → 投稿前检查 → 终审。
2. 人工修复留痕：运行期间允许开发者修平台代码或处理项目目录，但每次都要记入 `docs/system_defects_and_remediation_log.md`（现象、原因、改动、提交），次数计入对比指标。用户的正常操作（回答问题、审批）不算人工修复。
3. 对比有效：各实验组实际运行的配置确实不同；实验方案在最终评估之前写定，最终评估只跑一次，或如实报告跑了几次。
4. 结果可信：主要结果全部来自 `results/final/` 的封存评估；论文里每个数字都能通过 `paper/claims.md` 追溯到结果文件；`tarlab tex check` 没有 FAIL（含图表与数据一致）；终审核对过论文数字与结果文件一致。
5. 预算和期限：不超过立项时确认的预算和期限，追加前先征得用户同意。
6. 中断恢复：运行中至少人为中断一次（杀进程或重启机器），平台能自动续跑，不丢已完成的工作。

#### 对比指标（只记录，不设门槛）

- 总耗时、花费、工单数、重试次数。
- 向用户提问的次数；跑完后由用户逐个标注“必要”或“不必要”，目标是不必要的问题不超过 1 个。
- 人工修复的次数（见门槛 2）；运行中出现的平台缺陷数及其中自行恢复的比例。
- 终审评分（1–10），以及另一个不同模型的独立审稿人的评分。
- 引用核验通过率；图表是否全部由数据生成。

#### 项目 B 重跑

- 沿用第零版的输入：一句话需求“帮我做一篇小型世界模型的论文，能在 8GB 显存上跑，达到 workshop 水平”，预算 50 美元，期限 24 小时。
- 第零版基准（账本记录）：花费 11.41 美元，运行约 4 小时，14 张工单共 16 次尝试，向用户提问 2 次；在假设检验前停止，只交付了技术报告，未通过第零版的完整流程验收。

#### 真实项目验收

- 由用户给出题目和目标会议；上述硬性门槛全部适用。
- 另加用户的主观判断：结果是否有用、论文是否值得投。是否达到目标会议水平由用户判断，平台审稿分只作参考。

## 15. 待定事项

- 主 Agent 的模型安排与成本平衡。
- 多 Agent 框架选型：在本文确认后，通过最小原型对比再定。
- 平台状态的存储方式（文件、SQLite 或数据库）。
- 止损和筛选规则的默认阈值。
- 项目 B 的具体环境与题目范围。
- Devin 订阅用于自动化调用的条款与额度。
- Undermind 刷新令牌在真实过期后的续期验证。
